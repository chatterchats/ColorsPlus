# Colors+ implementation strategy review

Review date: **October 4, 2026 (America/New_York)**. Scope: architecture assessment of the active **Colors+Probe v0.2.113**, not a migration or release. Repository: `/run/media/chats/e0057d4a-fe46-43eb-a837-db51979c500f/ZComMods/Colors+`.

## Recommendation and confidence

For a **new implementation of the same requirements with today's verified tools**, I would choose **UE4SS Lua for runtime UI/workflow and customization transactions, supported by SWZC SDK inspection and offline reference generation**. I would design an explicit, replaceable input/view boundary from the start. I would not begin with a full native port or make cooked UI a prerequisite.

For this mod, retain that architecture now. First measure v0.2.113 on matched presets, strengthen the weaker recovery-file writers, and clarify the transaction/backend boundaries. Consider a **small UE4SS C++ input or read/validation helper** only if it demonstrates a remaining cost or capability that improved Lua cannot adequately address. Do not port the color math for speed. Do not start a full runtime rewrite to evaluate one hot path.

**Confidence: moderate to high in the current recommendation; low in any quantitative native speedup estimate.** The strongest reason is the distribution of responsibilities: most correctness complexity belongs to live game ownership, native fragment replacement, preview donors, material dispatch, and native saving. Changing languages does not remove those responsibilities. Lua already reaches the required game operations, and recent improvements remove repeated discovery without sacrificing fresh validation. The actual native replacement has no Colors+ parity/performance proof, while the proposed SDK picker has unresolved authoring, Windows cook, loading, and CommonUI steps.

This gives no weight to past development time. The current implementation matters because it supplies executable behavior, regression cases, and native observations. A smaller, demonstrably better native component would deserve adoption even if it replaced substantial Lua. A complete SDK UI could become the preferable view implementation once its delivery and input route are proven.

The strongest counterargument is that continuous mouse interaction is a poor fit for hundreds of reflected widget operations and sampled input. A native implementation could batch reads, use stronger object identities, improve diagnostics, and potentially replace the 384-button SV surface with one correctly integrated control. That is a credible capability argument, stronger than “C++ is faster.” It would overturn the view/helper recommendation if a bounded prototype proves those benefits on this loader with materially better responsiveness and complete lifecycle parity. It does not yet justify moving saving, recovery, or race-specific transactions.

## Current-code assessment

### Strengths supported by source and tests

1. **Mutation authority is explicit.** `resolve`, `verify_unchanged_context`, `source`, and `check_source` verify live relationships rather than trusting a selected label or the first global object. Stock definitions/material parents are not the tint mutation destination.
2. **Native calls are treated as replacement boundaries.** `update_owned_color` validates before the write, reacquires after it, refreshes, and validates again. Zabrak's `set_order` persists an in-flight phase and adopts new identities only from the verified return boundary. This addresses game behavior a C++ rewrite must also handle.
3. **Source ownership and display availability are distinct.** `editor_session.watch` can retain a valid Apply while display state is temporarily absent during radial navigation, uses a finite rendering retry budget, and preserves later external edits.
4. **Lifetime hardening is substantive.** UI frame reuse releases wrappers before tint setup and between callbacks; scalar-only jobs, cancellation keys, same-process markers, and full-name/attachment gates reduce stale-reference risk. Current v0.2.113 reuse invalidates routes on native events and refuses callbacks occurring during discovery.
5. **Recent input fixes address real mechanisms.** Native Apply/Cancel click intent survives until the next tick; Apply flushes the latest value; supported profiles coalesce preview work behind a 75 ms post-update cooldown and a separate 495 ms health gate. This removes dependence on seeing Apply held during a poll.
6. **Regression coverage is unusually relevant to this domain.** Mocks include replaced owners/fragments, companion preservation, failure rollback, malformed journals, old formats, action retirement, and context-hint fallback. The allowlisted packaging tool prevents accidentally shipping a local recovery record.

## Candidate architectures

### A. Improved UE4SS Lua runtime — supported current choice

Keep UI/workflow and all fragment transactions in Lua; use SDK reports to improve schema understanding and offline test fixtures. Functional coverage is the current supported behavior described above, with preset-specific persistence gaps unchanged. Improve source boundaries/journals and measure v0.2.113 before adding new runtime dependencies.

Distribution remains scripts, manifests, PNG assets, and the installed UE4SS loader. No Windows native compiler is needed for Colors+ releases. Reflection/class/path changes still require updates; this route is not update-proof. It retains the tested native parents, focus/input environment, journals, and stock save semantics.

**Best argument:** complete reachable feature set with the fewest unverified delivery steps; measured expensive discovery is already reduced by design changes. **Best objection:** sampled input, runtime UI construction, and binding overhead can remain limiting even after careful Lua improvements.

### B. Full UE4SS C++ runtime — plausible, conditional, not recommended now

This means a **Windows x64 injected native mod DLL**, not a reconstructed SDK editor module. It would move the launcher/view, input queue, discovery, profiles, preview/source transactions, journals, recovery, consoles, and lifecycle ownership into one native mod. It must keep using the shipped game objects/functions; reconstructed native stubs are not substitutes.

The precise examined API is upstream commit **a1e7f571**: `UE4SS/include/Mod/CppUserModBase.hpp`, `UE4SS/src/Mod/CppMod.cpp`, `UE4SS/src/UE4SSProgram.cpp`, and `UE4SS/src/Mod/LuaMod.cpp`. Installed DLL exports corroborate `CppUserModBase` constructor/destructor and lifecycle/Lua callbacks. The native loader resolves `dlls/main.dll` (or the mod-name DLL), requires exported `start_mod` and `uninstall_mod`, and ultimately frees the module. Unreal access starts after `on_unreal_init`; startup must not perform game-object work prematurely.

At this revision, `on_update()` is dispatched by UE4SS's event loop, which sleeps between iterations. **Do not use it for UObject/UMG mutation.** The implementation uses `RC::Unreal::Hook::RegisterEngineTickPreCallback` for Lua game-thread actions, with a ProcessEvent route available. A native port needs a bounded game-thread queue/tick callback, cancellation/generation tokens, deferred CommonUI intent, and hook-registration removal/quiescence before unloading. The precise native unregistration/weak-pointer interfaces remain to be verified from the matching dependency headers; no safe unload prototype was run.

Build/link target: pinned UE4SS **`Game__Shipping__Win64`**, C++23, CMake ≥3.22, ABI-compatible Windows SDK/MSVC toolchain and dynamic release CRT, link to the matching UE4SS import library/target. The pinned version checks specify MSVC toolset 14.43 and Rust ≥1.73 for rebuilding dependencies; clang-cl is accommodated but cross-compilation requires a demonstrated Windows/CRT/dependency setup. CMake and Ninja are on PATH here; `cl`, `clang-cl`, `lld-link`, and MinGW cross-g++ are not. The installed compatibility archive includes **no headers or import library**.

UE4SS's Unreal layer is the separate **UEPseudo** gitlink `885ba757bf8ddcc1599a7b0be770fe2ec1143d4f`, alongside other build dependencies. Unauthenticated retrieval returned HTTP 404; its exact headers/build access have not been established here. This is a prerequisite to verify, not proof native modding is impossible. The SWZC reconstructed `UCLASS` headers compiled by UBT are **not** those UE4SS dependencies. Directly casting shipping objects to reconstructed C++ layouts or linking their empty setters is unjustified. Begin with verified UE4SS reflection/ProcessEvent parameter layouts, then prove any stronger typed access independently.

**Best argument:** unified typed implementation can batch reflection, use verified serial identities, improve native diagnostics, and remove interpreter/marshaling work. **Cost:** all transaction/race/save/recovery parity must be recreated, Windows ABI becomes a release contract, and native pointers/hooks can introduce harder crashes. A full port using the same 431-widget construction and native refresh algorithm retains much of the existing cost. Neither performance nor reliability superiority is measured.

### C. SDK-authored runtime content — conditional UI future; blocked current delivery

A concrete useful candidate is a **new picker view asset**, proposed `/Game/Mods/ColorsPlusUI/WBP_ColorsPlusPicker.WBP_ColorsPlusPicker_C`, with hue/SV/hex controls and action controls. Use `/Script/UMG.UserWidget` as the initial eligible parent; a new CommonActivatableWidget child would require separately proving stack, focus, back, and activation semantics. Host it in the same validated item-page `SelectionTiles` overlay, rather than replacing `/Game/Game/UI/Strategy/Customization/Widgets/New/WBP_Customization_ItemPage` or the creator master.

Existing style/callback dependencies would include:

- `/Game/Game/UI/Strategy/Customization/Widgets/New/WBP_Customization_SlotSubItemName.WBP_Customization_SlotSubItemName_C` and its `BitReactorRichTextBlock`;
- `/Game/Game/UI/Strategy/Customization/Widgets/CharacterDatabank/WBP_CharacterDataBank_TopNavButton.WBP_CharacterDataBank_TopNavButton_C` and CommonUI;
- native UMG/input libraries and any proven new SV input control/material/texture resources;
- the shipping customization providers and all transaction targets listed earlier. The UI asset would not implement their native save or material behavior.

The authoring route would create a new local lab widget, compile/save/reopen it, and independently inspect/test the exact parents, templates, styles, and bindings. Sanitized reconstruction of the existing heading is not yet established: tested widget reconstructions fail on `BitReactorRichTextBlock`. Writing a new native-only widget might avoid that particular dependency, but loses inherited styling/behavior and still requires its own proof. Editable B1 gameplay-child success is not widget-child success.

Required delivery is a **game-compatible Windows cook**, including shader/platform data if a custom SV material is used, matching release/native-parent references and a content-only package with a unique mount/path. The delivered Linux editor explicitly rejects the Windows cook target. Its isolated Linux curve `.uasset`/`.uexp` route proves neither a Windows widget cook nor a shipped-parent cook. Old Win64 modkit editor binaries do not establish a working current Windows cook target.

A proposed `.pak` route is `Content/Paks/LogicMods/ColorsPlusUI.pak`, containing `/Game/Mods/ColorsPlusUI/ModActor.ModActor_C` if the installed BP loader is chosen. That loader constructs this path and spawns the actor after map load. Its presence does not prove this proposed package mounts, its dependencies resolve, or its callbacks work; the inspected LogicMods directory is empty. Alternatively Lua could load a proven mounted widget class directly. A content-only plugin mount or IoStore container route must separately establish loader registration/mounting; do not assume every `.pak` or editor plugin descriptor is sufficient.

Connect the view back to Lua through named reflected scalar getters/intent fields and deferred click routing, or through a proven native bridge. The view owns presentation/input only; the existing transaction owner validates/updates/applies/restores. A `ModActor` must not duplicate saving or fragment authority. Stock game/Character Suite providers remain necessary. Compiling the Linux Editor inspector/workbench plugins produces development tools, not a DLL the Windows shipping executable will load.

**Best argument:** authoring layout/input can remove imperative UI assembly and improve navigation/scale behavior. **Current blockers:** exact widget/parent/callback proof, Windows cook and external-parent/native-provider workflow, package loading, and live CommonUI integration. Original shading is also unverified, so a shader-based SV control adds a further prerequisite. A palette/data-only asset adds no clear advantage for continuous per-character tinting unless a saved palette feature is intentionally introduced.

## Current action and reconsideration conditions

There is no recommended migration phase now. Useful targeted work, in order:

1. Capture matched v0.2.113 responsiveness and input correctness; keep first/cold/warm openings and source-swap/ordinary paths separate. Add monotonic wall measurement and bounded scan/crossing counts only where they resolve attribution. Do not infer user activity duration from `picker.sample` rows.
2. Unify safe journal replacement/error handling for the ordinary preview and Default-selection writers, with old-format reading and failure-injection coverage. This is valuable in every candidate.
3. Make view/input and transaction backends explicit, documenting source-draft versus clone-preview ownership, immutable original values, mutation phases, valid native replacement handoffs, and receipt expiry. Reduce redundant module/journal utilities without weakening the proven transaction checks.
4. Maintain a current feature/preset proof matrix and tested loader/game/provider identities. Keep historical plans available but visibly versioned; separate optional probes from production responsibilities when preparing a release.

Reconsider a native helper if current wall/crossing evidence shows sustained input/discovery/validation cost that batching can remove, or if a serial-safe input/identity capability proves materially better. Reconsider an authored view if exact Windows cook/mount and CommonUI/input proof succeed. Reconsider a full C++ runtime only if those smaller proofs show a broader native engine ownership design genuinely reduces total complexity and passes complete parity—not merely because Lua source is large.
